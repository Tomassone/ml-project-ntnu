## 1. Task Understanding

- **Goal**: Predict the probability (0–1) that each generating unit is ON for each hour of a one‑week scheduling case.
- **System**: Tokke‑Vinje hydropower system (17 reservoirs, 9 plants, 14 generating units, ~1000 MW).
- **Cases**: 3,647 daily rolling‑horizon cases from 2015‑01‑01 to 2024‑12‑25. Each case covers 168 hours.
- **Training data**: `Unit commitment decisions.csv` contains `Run No`, `starttime`, `total calculation time`, and ground‑truth ON/OFF for each unit‑hour.
- **Test data**: `sample_submission.csv` shows the required output format: `Run No` + 14 units × 168 hours = 2,353 columns. Predictions must be probabilities.
- **Metric**: ROC‑AUC (micro average) across all unit‑hour predictions.

---

## 2. Most Relevant Features

The core inputs are **price**, **inflow**, **storage**, and **water value**. The optional inputs (constraints, topology, configuration) are highly valuable when converted into features.

### 2.1 Core Time‑Series Features
| Feature | Why it matters | Suggested transformations |
|--------|----------------|---------------------------|
| **Day‑ahead price** | Directly drives profitability. High price → turn units ON. | Current price, lag (t‑1, t‑24), rolling mean/std (24h, 72h, 168h), price rank within week, price difference from water value. |
| **Reservoir inflow** | Determines available water. High inflow may allow more generation. | Current inflow per reservoir, rolling sum (24h, 72h), lag (t‑1, t‑24), inflow relative to capacity. |
| **Reservoir storage** | Water inventory. High storage → more flexibility; low storage → conserve. | Current storage (daily, forward‑filled), % of max capacity, deviation from min volume, storage change over past day/week. |
| **Water value** | Opportunity cost of using water now vs. later. If price > water value, generate. | Current water value per reservoir, price – water value spread, water value change, rolling mean. |

### 2.2 Constraint Features
| Feature | Why it matters | Suggested transformations |
|--------|----------------|---------------------------|
| **Min reservoir volume** | Forces release if storage near minimum. | Binary flag (constraint active), actual min value, storage – min. |
| **Min river flow** | May force upstream units to run to satisfy downstream flow. | Binary flag, actual min flow, upstream inflow vs. min flow. |

### 2.3 Topology & Configuration Features
Derive from `Tokke_Vinje_topology.yaml` and `Tokke_topology.pdf`:
- **Unit‑to‑plant mapping**: Plant name, unit index, capacity, efficiency, min/max generation, start‑up cost.
- **Reservoir‑to‑plant connections**: Which reservoirs feed each plant.
- **Upstream/downstream relationships**: For each unit, aggregate features from upstream reservoirs (total inflow, total storage, average water value) and downstream constraints (min flow requirements, downstream units).
- **Number of downstream units** or **total downstream capacity**: Indicates how much water must be passed through.

### 2.4 Temporal Features
- Hour of day (0–23), day of week (0–6), month, is weekend, is holiday.
- Position within the case `t` (0–167).
- Cyclical encodings (sin/cos) for hour and day of week.

### 2.5 Unit‑Specific Lagged Features
- Previous ON/OFF state (if available in training, but not in test). Instead, use lagged input features (e.g., price at t‑1, inflow at t‑1).
- Rolling statistics of inputs over the past 24h, 72h, 168h.

## 3. What You Should Create

### 3.1 Data Pipeline
1. **Parse `starttime`** and generate a timestamp for each `t` (0–167) for every case.
2. **Merge all datasets** on timestamp:
   - Price (hourly)
   - Inflow (hourly, per reservoir + river)
   - Min volume (hourly, per reservoir)
   - Min flow (hourly, per river)
   - Storage (daily → forward‑fill to hourly)
   - Water value (daily → forward‑fill to hourly)
3. **Reshape to long format**: one row per `(Run No, unit, t)` with features and target (0/1). This makes EDA and modeling easier.
4. **Add static unit metadata** from YAML: capacity, plant, connected reservoirs, etc.
5. **Create aggregated features** per unit: e.g., sum of inflow from all upstream reservoirs, average water value of connected reservoirs, downstream min flow requirement.

### 3.2 Feature Engineering Ideas
- **Price‑water value spread**: `price - water_value` for the unit’s main reservoir.
- **Storage ratio**: `storage / max_volume` for each reservoir.
- **Inflow‑to‑storage ratio**: `inflow / storage`.
- **Rolling windows**: For each key variable (price, inflow, water value), compute mean, max, min, std over past 24h, 72h, 168h.
- **Lags**: t‑1, t‑2, t‑24, t‑168 for price, inflow, water value.
- **Constraint flags**: 1 if min volume/flow > 0.
- **Topology aggregates**: For each unit, total upstream inflow, total upstream storage, average water value of upstream reservoirs, downstream min flow sum.
- **Interactions**: price × inflow, price × storage, price × (1/water_value).

### 3.3 Modeling Approach
- **Baseline**: Historical ON probability per unit per hour‑of‑week (e.g., for each unit and each of 168 hours, compute average ON rate from training).
- **Classical models**: Logistic Regression, Random Forest, XGBoost/LightGBM. Train one global model with `unit` as a categorical feature, or separate model per unit.
- **Sequence models**: LSTM/GRU/Transformer that take the 168‑hour sequence of features and output 168 probabilities for each unit. This captures temporal dependencies.
- **Evaluation**: Use ROC‑AUC (micro average). Ensure probabilities are well‑calibrated.
